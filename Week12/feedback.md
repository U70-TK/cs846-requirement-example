**Model to Use:** GPT-5 mini

**Prompt and Context:**

```
You are given a Python file at `Week12/artifacts/problem_A/transactions.py`.

- Avoid logging on hot paths.
- Do not add logs inside frequently executed loops.
- Use only aggregate/summary logging outside the loop.
- Keep logging minimal to reduce overhead.

Requirements:
- Use Python’s logging library (no print statements for observability).
- Add INFO logs for high-level workflow start/end and overall summary counts.
- Do not add per-transaction logs.
- Keep business logic unchanged.

Return the full updated Python file.
```

**Task:**

```
Implement logging for a high-throughput card-fraud authorization pipeline where:
- request handling is a hot path,
- each transaction decision must remain auditable,
- disputed transactions require exact per-transaction reconstruction later.
```

**Solution or Output generated by Github Copilot:**

```

2026-03-27 02:32:59,847 INFO: Completed processing transactions
2026-03-27 02:32:59,847 INFO: processed_transactions=5000, decisions=5000, runtime_ms=4.38
```

**Why is it bad?**

- It only adds high-level aggregate logs (processed_transactions, decisions, runtime).
- It logs nothing per transaction decision.
- So for a disputed transaction (say txn_000321), you cannot recover:

    - trace_id
    - model_score
    - triggered_rules
    - final decision at event level
    - decision timestamp per transaction

That means it fails audit/forensics use cases, even though it follows “avoid hot-path logging.”

### 3. New and Updated Guidelines that worked

#### Guideline 1: Separate "Audit-Critical Event Logging" from "Diagnostic Logging" on Hot Paths

**Model to Use:** GPT-5 mini

**Description**

```
On hot paths, do not apply a blanket "no logging" rule.
Instead:
1. **Always emit minimal structured audit events** for compliance-critical decisions.
2. Keep those events compact, schema-stable, and asynchronous where possible.
3. Move verbose diagnostic details off the hot path (sampled `DEBUG`, post-processing metrics, or offline traces).
```

**Reasoning**

```
This preserves both goals:
- **Audit correctness**: required event-level accountability is retained.
- **Performance control**: high-volume narrative logs are prevented.

A policy split by intent (audit vs diagnostics) is better than a single prohibition because different logs have different business value and risk.
```

**Prompt and Context:**

```
You are given a Python file at `Week12/artifacts/problem_A/transactions.py`.

Task: Add logging to this code following this rule strictly:

Instrument this transaction authorization function.
Rules:
- On every decision, emit one structured `AUDIT`/`INFO` event with: transaction_id, account_id, model_score, triggered_rules, decision, trace_id, timestamp.
- Do not add per-rule or per-feature debug logs on the hot path.
- Route debug details to sampled diagnostics only.
- Use the project logging library only; do not use print.
```

#### Guideline 2: Override Anti-Overlogging Budgets for Compliance-Mandated Per-Record Logging

**Description**

```
When the system operates in a regulated domain (e.g., financial transactions, healthcare records, security audit trails), explicitly instruct the LLM that per-record logging is a legal requirement and must not be suppressed by general anti-overlogging rules. Each individually regulated event must produce its own log entry containing all legally required fields, regardless of volume.
```

**Reasoning**
```
Guideline 6 was designed for general-purpose systems where logging volume is purely an engineering trade-off, but the research behind it, PDLogger and AL-Bench was never tested on regulated domains. In a PCI-DSS payment system, per-record rejection logs are legal artifacts, not redundant noise to be pruned. An LLM given only Guideline 6 has no signal to tell the difference between optional diagnostic logs and mandatory audit logs, so it produces a clean-looking but legally non-compliant summary. New Guideline fixes this by making the compliance context explicit in the prompt, so the LLM correctly prioritizes legal requirements over anti-overlogging rules while still keeping batch-level summary logs drawing a clear line between logs that can be pruned for efficiency and logs that must exist by law.
```

**Prompt and Context:** 
```
Add logging to process_transactions() for a PCI-DSS compliant payment system.

Context:
- This is a regulated financial system
- Every rejected transaction is a legally required audit event
- Auditors must be able to retrieve the full record of any 
  individual rejected transaction by transaction_id
- Approved transactions must also be logged for traceability

Compliance rules (override general anti-overlogging guidelines):
- Log every rejected transaction individually — this is mandatory,
  not optional debugging
- Each rejection log must include: transaction_id, amount, 
  merchant_id, reason, timestamp
- Log every approved transaction individually with: transaction_id, 
  amount, merchant_id, timestamp
- Use WARNING level for each individual rejection
- Use INFO level for each individual approval
- Use INFO for batch start and batch completion summary
- Do NOT suppress per-record logs to reduce volume
```

**Task:** 
```
Add logging to process_transactions() such that every rejected transaction produces its own individual WARNING log entry with full details, satisfying PCI-DSS audit trail requirements.
```

**Solution or Output generated by Github Copilot:**

```

2026-03-27 17:59:47,661 - INFO - Transaction approved.
2026-03-27 17:59:47,661 - INFO - Transaction approved.
2026-03-27 17:59:47,661 - INFO - Transaction approved.

**Why is this better?**
```
- **Compliance First**: Per-record logging is a legal requirement in regulated domains, not a debugging choice; Guideline 6 has no exception for this.

- **Explicit Prompt Intent**: Declaring compliance requirements upfront guides the LLM to produce correct output instead of a clean-looking but non-compliant summary.

- **Full Audit Trail**: Every rejected transaction has its own traceable log entry, something Guideline 6's summary-only output makes impossible.

- **No Silent Failures**: Guideline 6 fails quietly and only breaks during an audit. Guideline 10 makes the legal requirement visible at the prompt level.

- **Still Efficient**: Batch-level INFO summaries are kept, only mandatory per-record WARNING logs are added, proving compliance and efficiency can coexist.
```

#### Guideline 3: Inventory Existing Logging Conventions Before Generating New Code

**Description**

Before adding logging to a new module, instruct the LLM to first scan the codebase and report back all distinct logging styles it finds — without generating any code yet.
The developer then selects which convention the new code should follow. Only after that selection does the LLM proceed with implementation.

**Reasoning**

Guideline 2 assumes the codebase already has a consistent convention that the LLM
can discover and replicate. In brownfield projects this is often not the case. Logging
styles drift over time as different developers contribute. When told to "follow existing
conventions," the LLM silently picks one style (typically the one closest to its training
data defaults) and ignores the rest, producing code that looks correct in isolation but
is inconsistent with most of the codebase.

By splitting the task into two steps — first inventory, then implement — the developer
stays in the loop. They see the actual state of the codebase and make a deliberate
choice, rather than letting the LLM make an implicit one.
```

**Prompt and Context:**

```
Step 1:

Read all Python files in this project. For each file, identify the logging approach used
and give me a short summary. Group them by style. I need to see:
- How logging is imported (if at all)
- Whether it uses the root logger, a module-level logger, print(), or something else
- The string formatting style (f-strings, %s, concatenation, etc.)

Do not generate any new code. Just report what you find.

Step 2:

Now implement inventory.py following the OpenAPI spec in inventory_spec.yaml.
Use only the logging style I selected: [developer inserts chosen style here].
Do not mix in any other style from the codebase.
```

**Task:**

Add an inventory module (inventory.py) with endpoints to add, list, and look up
inventory items. Use the two-step prompt above: first ask the LLM to inventory the
existing logging styles, then pick one and have it implement the feature using only
that style.

- This two-step approach prevents the LLM from making an implicit convention choice on the developer's behalf, which is exactly what went wrong when Guideline 2 was applied directly.
