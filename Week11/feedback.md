#### Guideline 4: Use Execution Profiler Traces for Optimizing a Program

**Prompt and Context:**

**Task:**
Optimize `top_urls_by_unique_users` for performance. The current implementation works on moderate input sizes, but it scales poorly because it stores a large `set` of users for every URL.

**Solution or Output generated by Github Copilot:**
```python
from __future__ import annotations

import random
import tempfile
import time
from collections import defaultdict
from pathlib import Path

# allow `@profile` from line_profiler when present, otherwise no-op
try:
    profile
except NameError:
    def profile(func):
        return func


def generate_log_file(path: Path, num_events: int = 2_000_000) -> None:
    rng = random.Random(42)
    urls = [f"/product/{i}" for i in range(5000)]

    with path.open("w", encoding="utf-8") as f:
        for _ in range(num_events):
            user_id = rng.randint(1, 400_000)
            url = urls[rng.randint(0, len(urls) - 1)]
            f.write(f"{user_id},{url}\n")


@profile
def top_urls_by_unique_users(path: Path, top_k: int = 100) -> list[tuple[str, int]]:
    # Intentionally memory-heavy baseline:
    # stores every distinct user_id for every URL.
    # Use a plain dict with bytes keys and manual set creation to avoid
    # defaultdict overhead and expensive unicode ops per line.
    # Collect (url_idx, user) pairs then sort to count unique users.
    url_to_idx: dict[bytes, int] = {}
    pairs: list[tuple[int, int]] = []

    with path.open("rb") as f:
        _int = int
        idx_get = url_to_idx.get
        for line in f:
            i = line.find(b',')
            user = _int(line[:i])
            url = line[i + 1 : -1] if line[-1] == 10 else line[i + 1 :]
            idx = idx_get(url)
            if idx is None:
                idx = len(url_to_idx)
                url_to_idx[url] = idx
            pairs.append((idx, user))

    # Sort pairs (C-optimized). Then count unique users per url by scanning.
    pairs.sort()
    counts_arr = [0] * len(url_to_idx)
    prev_idx = -1
    prev_user = -1
    for idx, user in pairs:
        if idx != prev_idx or user != prev_user:
            counts_arr[idx] += 1
            prev_idx = idx
            prev_user = user

    counts = []
    for url, idx in url_to_idx.items():
        counts.append((url.decode("utf-8"), counts_arr[idx]))
    counts.sort(key=lambda item: item[1], reverse=True)
    return counts[:top_k]


def main() -> None:
    with tempfile.TemporaryDirectory() as tmpdir:
        path = Path(tmpdir) / "events.csv"
        generate_log_file(path)

        start = time.perf_counter()
        result = top_urls_by_unique_users(path)
        elapsed = time.perf_counter() - start

        print(f"Computed top {len(result)} URLs in {elapsed:.3f}s")
        print(result[:5])


if __name__ == "__main__":
    main()
```

**Why this Solution is Bad**
1. The main bottleneck is memory, not CPU time.
`line_profiler` measures time spent per line. It does not tell the model which data structures are causing peak memory growth, object churn, or out-of-memory failure.

2. The baseline program may not finish at all.
In [top_urls_by_unique_users.py], the baseline stores a `set[int]` for every URL. On larger real inputs, that representation can exceed the memory budget before a useful profiling trace is produced.

3. The trace can point at symptoms instead of the real design flaw.
The hottest line will likely be `users_per_url[url].add(int(user_id_text))`, but the real issue is architectural: the code keeps too much exact state in memory. Making that line marginally faster does not solve the scaling problem.

4. It biases the model toward local edits.
Guideline 4 encourages "optimize what the profiler highlights." For this task, the correct move is likely a redesign around streaming, partitioning, or an external aggregation strategy. The profiler-first workflow makes that less likely.

5. It ignores the resource constraint that actually defines success.
For this question, a program that is 20% faster but still exceeds memory is a failure. Guideline 4 treats performance mainly as runtime improvement, so it does not optimize for the real objective.

6. It also makes the model's search process inefficient as it takes too long to converge on a final solution now.

#### Guideline 3: Explicitly ask it to optimize for worst-case input size while preserving correctness.

**Task Description:**
Ask the LLM to optimize `count_active_users` under an explicit worst-case framing: the input may be much larger than RAM, correctness must be preserved exactly, and bounded peak memory should be prioritized even if the implementation becomes more complex.

By explicitly prioritizing worst-case scalability, the prompt may steer the model toward an external-memory or disk-backed design that is robust on oversized inputs but imposes avoidable I/O and bookkeeping costs on the much more common case where the data fits comfortably in memory. **Task:** 
Optimize `count_active_users` for performance. The function must return the exact number of distinct users who appear at least `min_events` times in an event log, while preserving correctness on large inputs that may exceed available RAM.

**Solution or Output generated by GitHub Copilot:**

```python
from __future__ import annotations

import random
import sqlite3
import tempfile
import os
from pathlib import Path


def generate_log_file(
    path: Path,
    *,
    num_events: int,
    num_users: int = 200_000,
    num_pages: int = 2_000,
    seed: int = 42,
) -> None:
    rng = random.Random(seed)
    pages = [f"/page/{i}" for i in range(num_pages)]

    with path.open("w", encoding="utf-8") as f:
        for event_index in range(num_events):
            timestamp = f"2026-03-22T{event_index % 24:02d}:{event_index % 60:02d}:00"
            user_id = rng.randint(1, num_users)
            page = pages[rng.randint(0, len(pages) - 1)]
            f.write(f"{timestamp},{user_id},{page}\n")


def count_active_users(path: Path, min_events: int = 3) -> int:
    """
    Return the exact number of users who appear at least `min_events` times.

    Input format:
    - One CSV record per line: "<timestamp>,<user_id>,<page>"
    - Example: "2026-03-22T13:45:00,42,/page/17"

    Required behavior:
    - Count total events per user exactly.
    - Return how many distinct users have at least `min_events` events.
    - Do not use approximations.

    Constraints for this task:
    - The full input may be much larger than available RAM.
    - The implementation must remain exact on very large files.
    - You may redesign the algorithm and data structures completely.

    Edit only this function.
    """
    # Create a temporary on-disk SQLite database to keep counts exact
    # while bounding memory usage. We stream the input file and
    # increment per-user counters in the database. Finally query how
    # many users have counts >= min_events.
    if min_events <= 0:
        raise ValueError("min_events must be positive")

    # Create temporary file for SQLite database
    with tempfile.NamedTemporaryFile(prefix="active_users_", suffix=".db", delete=False) as tf:
        db_path = tf.name

    try:
        conn = sqlite3.connect(db_path)
        # Reduce durability overhead — safe for a local temp DB.
        conn.execute("PRAGMA journal_mode = MEMORY")
        conn.execute("PRAGMA synchronous = OFF")
        conn.execute("CREATE TABLE counts (user_id INTEGER PRIMARY KEY, cnt INTEGER NOT NULL)")
        cur = conn.cursor()

        batch = 0
        commit_batch = 10000
        with path.open("r", encoding="utf-8") as f:
            for line in f:
                line = line.rstrip("\n")
                if not line:
                    continue
                parts = line.split(",", 2)
                if len(parts) < 2:
                    continue
                try:
                    user_id = int(parts[1])
                except Exception:
                    # Skip malformed user ids
                    continue

                # Use SQLite upsert to increment the counter exactly on disk.
                cur.execute(
                    "INSERT INTO counts(user_id, cnt) VALUES (?, 1) ON CONFLICT(user_id) DO UPDATE SET cnt = cnt + 1",
                    (user_id,),
                )
                batch += 1
                if batch >= commit_batch:
                    conn.commit()
                    batch = 0

        if batch:
            conn.commit()

        cur.execute("SELECT COUNT(*) FROM counts WHERE cnt >= ?", (min_events,))
        result = cur.fetchone()[0]
        conn.close()
        return int(result)
    finally:
        try:
            os.remove(db_path)
        except Exception:
            pass
```

**Why it's bad:**
1. The solution is correct, but it optimizes the wrong objective.
The prompt strongly emphasized worst-case memory behavior, so the model chose a disk-backed SQLite solution instead of the much simpler in-memory dictionary counter. That makes the implementation more robust to oversized inputs, but sometimes the algorithm optimization towards worst-case scenario and the algorithm optimization towards average-case scenario are totally divergent. 

2. This design hurts average performance substantially.
Running `python run_benchmark.py` produced the following results:
`50,000` events: `4.95x` slower
`100,000` events: `3.66x` slower
`200,000` events: `3.85x` slower
`400,000` events: `4.14x` slower
Weighted average latency: `4.07x` slower than the common-case reference.

3. For this task, optimizing for worst-case input size and optimizing for average-case runtime are not aligned. The prompt makes the model overvalue rare oversized inputs and undervalue the cheaper in-memory solution that wins on typical workloads.

#### Guideline 2: State the memory budget and require memory-aware optimization before runtime tuning

**Description:**
When the task involves large inputs, explicitly tell the LLM the available memory budget and whether the input can fit in memory. Ask it to first identify the peak-memory sources in the current approach, then redesign the solution to stream, batch, or externalize state as needed before attempting micro-optimizations.

**Reasoning:**
Large-scale performance problems are often constrained by memory, not raw CPU time. If the model is not told about the memory limit, it may generate a fast-looking solution that still materializes huge intermediate structures and fails in practice. A memory-aware prompt pushes the model to reason about space complexity, data lifetime, and I/O strategy, which are central to performance on oversized datasets.

**Prompt and Context:**
The current program is too slow and may exceed memory limits on full-scale input.
Assume the input file is much larger than RAM and the machine has a strict 512 MB memory budget.
First, identify which parts of the current approach cause the highest space usage and why.
Then redesign the solution to minimize peak memory usage, using streaming, batching, or external aggregation if needed.
After that, optimize runtime within the memory budget while preserving exact correctness.

**Task:**
Optimize `top_urls_by_unique_users` for performance. The current implementation works on moderate input sizes, but it scales poorly because it stores a large `set` of users for every URL.

**Solution or Output generated by Github Copilot:**
```python
from __future__ import annotations

import random
import tempfile
import time
from collections import defaultdict
from pathlib import Path


def generate_log_file(path: Path, num_events: int = 2_000_000) -> None:
    rng = random.Random(42)
    urls = [f"/product/{i}" for i in range(5000)]

    with path.open("w", encoding="utf-8") as f:
        for _ in range(num_events):
            user_id = rng.randint(1, 400_000)
            url = urls[rng.randint(0, len(urls) - 1)]
            f.write(f"{user_id},{url}\n")


def top_urls_by_unique_users(path: Path, top_k: int = 100) -> list[tuple[str, int]]:
    """
    Memory-friendly exact top-k by unique users per URL.

    Approach (external partitioning):
    - Partition the input file into N on-disk buckets by hashing the URL.
      This ensures we only materialize user-id sets for URLs inside a single
      partition at a time, reducing peak memory.
    - For each partition, build sets of user ids per URL, compute counts,
      and maintain a global min-heap of size ``top_k`` for the top results.

    This preserves exactness and streams the input; tune `num_partitions`
    if you need a different memory/IO tradeoff.
    """
    import heapq

    # Tunable: number of on-disk partitions. More partitions -> lower peak memory
    # per partition but more disk files and I/O. 128 is a reasonable default.
    num_partitions = 128

    with tempfile.TemporaryDirectory() as tmpdir:
        part_paths = [Path(tmpdir) / f"part_{i}.csv" for i in range(num_partitions)]

        # Phase 1: stream input and partition to disk by url-hash
        part_files = [p.open("w", encoding="utf-8") for p in part_paths]
        try:
            with path.open("r", encoding="utf-8") as f:
                for line in f:
                    user_id_text, url = line.rstrip("\n").split(",", 1)
                    idx = (hash(url) % num_partitions)
                    # write as url,user_id to partition
                    part_files[idx].write(f"{url},{user_id_text}\n")
        finally:
            for pf in part_files:
                pf.close()

        # Phase 2: process each partition independently, keeping only one
        # partition's user sets in memory at a time. Maintain a global min-heap
        # of size top_k to track overall top URLs.
        top_heap: list[tuple[int, str]] = []  # (count, url) min-heap

        for p in part_paths:
            if not p.exists():
                continue

            users_per_url: dict[str, set[int]] = defaultdict(set)
            with p.open("r", encoding="utf-8") as pf:
                for line in pf:
                    url, user_id_text = line.rstrip("\n").split(",", 1)
                    users_per_url[url].add(int(user_id_text))

            # push counts from this partition into the global top-k heap
            for url, users in users_per_url.items():
                cnt = len(users)
                if len(top_heap) < top_k:
                    heapq.heappush(top_heap, (cnt, url))
                else:
                    # pushpop to keep heap size bounded
                    if cnt > top_heap[0][0]:
                        heapq.heapreplace(top_heap, (cnt, url))

            # free memory for this partition explicitly
            del users_per_url

        # Sort final heap into descending order
        top = sorted(top_heap, key=lambda item: item[0], reverse=True)
        return [(url, cnt) for cnt, url in top]


def main() -> None:
    with tempfile.TemporaryDirectory() as tmpdir:
        path = Path(tmpdir) / "events.csv"
        generate_log_file(path)

        start = time.perf_counter()
        result = top_urls_by_unique_users(path)
        elapsed = time.perf_counter() - start

        print(f"Computed top {len(result)} URLs in {elapsed:.3f}s")
        print(result[:5])


if __name__ == "__main__":
    main()
```


**Why this Solution is Good**
1. It matches the real bottleneck.
The question is defined by a 512 MB cap, so the guideline focuses the model on the condition that actually determines whether the program works.

2. It encourages the right class of solution.
Instead of line-level tweaks, it pushes the model toward streaming, chunked processing, bounded dictionaries, sort-and-merge approaches, or other designs that can handle data larger than RAM.

3. It prevents false wins.
A solution that benchmarks well on a small sample but crashes on the full dataset is not a real optimization. This guideline reduces that failure mode.

4. It is likely useful beyond this one task, but needs validation.
The same prompting pattern may transfer to workloads like large CSVs, logs, graph edges, and ETL pipelines where peak memory is the main constraint; however, this should be treated as a hypothesis until verified with additional experiments or references.

5. It improves practical efficiency.
In this case, the guideline produced code that runs efficiently under the memory limit, and it also reduced iteration time by steering the model toward a viable strategy way earlier than Guideline 4.

6. It matches the evidence from this example.
In this counterexample, the core difficulty is not finding a slightly faster hot loop. It is recognizing that the state representation must be chosen around the memory limit. This guideline is better because it pushes the model toward that reasoning directly.

**Description:**
When a performance task is underspecified, first require the LLM to pause and explain whether optimizing for worst-case inputs and optimizing for average-case workloads point toward different algorithmic choices. If they do, the model should explicitly tell the developer that these goals may conflict, summarize the tradeoff, and ask the developer which objective should take priority before writing code.

**Reasoning:**
Optimizing for the worst case is not the same as improving average-case performance. In some tasks, the algorithm or data structure that is safest under extreme inputs can add overhead that makes typical workloads slower. If this tradeoff is not stated explicitly, the LLM may subconsciously treat worst-case robustness as the default optimization target and produce a solution that is correct but worse on the average case the developer actually cares about. A multi-turn prompt is better because it forces the model to explain this tradeoff and align with the developer on which objective should come first before making changes.

**Prompt and Context:**
```
You are optimizing a Python function for performance.

Before writing or changing any code, do not implement immediately.
First, analyze whether optimizing for worst-case input size and optimizing for average-case runtime would lead to different algorithmic choices for this task.

If they would lead in different directions:
1. Explicitly say that these are two different optimization objectives.
2. Explain, in concrete algorithmic terms, what kind of solution each objective would favor.
3. Explain the likely tradeoff in runtime, memory, and implementation complexity.
4. Ask the developer to choose which objective should take priority.
5. Do not write code until the developer answers.

If they would not lead in different directions, explain why and then proceed.

After the developer chooses an objective, implement the solution that matches that objective and justify why the chosen algorithm fits it.
```

**Task:** 
Apply this prompting pattern to `count_active_users` in `Week11/artifacts/problem_C/active_user_count.py`, where the function must return the exact number of distinct users who appear at least `min_events` times in a log. The goal is to force the LLM to tell the developer that a worst-case-memory-aware solution may favor an externalized or disk-backed counting strategy, while an average-case-optimized solution may favor a simple in-memory dictionary counter, and then let the developer explicitly choose which direction to pursue.

**Why this is better?**
1. It prevents silent objective mismatch.
Instead of silently treating "performance" as one fixed objective, the model must explicitly state whether it is optimizing for worst-case robustness or average-case speed.

2. It exposes the real algorithmic fork before coding begins.
In many tasks, worst-case optimization and average-case optimization do not differ by small refinements. They point toward genuinely different algorithmic directions, such as externalized, bounded-memory processing versus a simple in-memory hash-based design.

3. It keeps the developer in control of the optimization target.
The developer, not the LLM, decides whether the priority is guaranteed behavior on oversized inputs or better latency on the workloads that occur most often.

4. It reduces misleading "successful" outputs.
Without this clarification step, the model can produce a solution that is correct yet still misaligned with the developer's real goal. Requiring the model to surface the tradeoff before implementation makes that failure mode easier to catch.
